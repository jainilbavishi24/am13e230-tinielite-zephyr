1. The project in plain English

One-sentence definition
This project turns a TI LP-AM13E230 microcontroller board into a reliable, testable edge-AI waveform classifier that runs a generated neural network partly on the chip's TINIElite NPU under Zephyr RTOS.

The input represents one waveform as 256 numerical samples. The host computer converts those floating-point samples into the signed 8-bit format expected by the model and sends them to the board over USB UART. The board runs inference and returns three signed scores in this fixed order:

Output indexClassMeaning
0SawtoothModel score for a sawtooth waveform
1SineModel score for a sine waveform
2SquareModel score for a square waveform

The largest score is treated as the predicted class. These values are signed int8 model outputs, not calibrated probabilities. The board also returns measured execution times and NPU interrupt counters so the host can verify that hardware acceleration actually occurred.

Edge AI means the inference is executed on the device at the edge of the system rather than sending the tensor to a cloud server. The PC currently supplies test data and checks results, but it does not perform the neural-network inference.

2. The engineering problem

The available starting point was not a complete application. The important supplied artifact was a TI/TVM-generated static library named mod.a, plus its generated C header and six test fixtures. The library contained compiled neural-network code, but a usable embedded system still needed all of the surrounding infrastructure.

What was available

  • LP-AM13E230 development board.
  • Arm Cortex-M33 and TINIElite NPU hardware.
  • Generated model archive mod.a.
  • Generated API header and quantization constants.
  • Six golden regression fixtures.
  • TI technical collateral and debug tools.

What was missing

  • Zephyr support for this preview board and SoC.
  • UART and pin-control drivers.
  • NPU power, memory, and interrupt integration.
  • A robust host-to-board protocol.
  • Timeout and deadlock recovery.
  • Reproducible WSL build, flash, test, and CI workflows.

The real project was therefore broader than “run a model.” It was a platform bring-up, device-driver, runtime-integration, communications, reliability, and validation project centered on a real edge-AI workload.

3.1 Model shape

  • Generated input tensor: (1, 1, 256, 1), signed 8-bit.
  • Generated output tensor: (1, 3), signed 8-bit.
  • The dimensions of size one are batch/channel layout details. The meaningful sample dimension is 256.

3.2 Quantization

Embedded accelerators commonly use integer arithmetic because it needs less memory and is efficient in hardware. The generated header defines this conversion:

input_int = clip(int((input_float + bias) × scale) >> shift, -128, 127)

bias  = -70.02075
scale = 187.0
shift = 6

The Python client reads these constants directly from the generated header instead of duplicating them manually. It applies C/Python integer truncation, performs the right shift, and clips the result to the valid int8 range. Matching preprocessing matters: even a correct model can give different outputs if the host uses a different scale, rounding rule, order, or data type.

3.3 What the output proves

The host compares all three returned bytes with the corresponding golden output. An exact match on the six fixtures proves that this firmware revision reproduces those six supplied references. It does not establish general accuracy on unseen data.

5.1 Why Zephyr?

Zephyr provides a standard device model, build system, compile-time hardware description, kernel synchronization, time conversion, reboot services, native simulation, and a large testing ecosystem. The alternative would be to write a completely bare-metal startup and scheduling environment. The project still requires low-level register work because AM13E230 support was unavailable in the pinned upstream revision.

5.2 What “out-of-tree” means

The board and driver support live in this repository rather than being copied into the upstream Zephyr checkout. Zephyr discovers the repository as a module through zephyr/module.yml. This prevents local patches from being mixed into millions of upstream lines, makes Git history focused, and allows a clean, pinned Zephyr checkout to reproduce the build.

5.3 Why the inference is hybrid

The generated runtime owns the graph. It performs orchestration and some operations on the Cortex-M33, while generated TINIElite kernels offload supported stages. The current ELF contains three convolution entry points and one average-pooling entry point, plus CPU-side generated functions. Five acknowledged NPU completions are observed per inference. Because the graph and sublayer schedule are contained in a binary archive, the documentation does not invent a layer-by-layer network architecture that cannot be independently inspected.

6. End-to-end execution flow

  1. Power-on: the Cortex-M33 begins Zephyr startup.
  2. Clock initialization: a pre-kernel routine safely configures flash wait states, starts the 25 MHz crystal, locks the PLL, and moves MCLK to 200 MHz.
  3. Driver initialization: Zephyr initializes pin routing, UNICOMM UART, TINIElite power/privilege/interrupt state, and application devices.
  4. Safety initialization: the application configures WWDT0 for an independent four-second reset and verifies the NPU device is ready.
  5. Readiness: the firmware drains stale UART bytes and sends a CRC-protected READY frame declaring 256 input bytes and three outputs.
  6. Host preprocessing: Python reads a float fixture and quantizes 256 values to int8.
  7. Request: Python sends a protocol-v2 frame containing type, sequence, payload length, tensor, and CRC-32.
  8. Validation: firmware checks UART errors, magic, version, type, length, deadline, and CRC.
  9. Acknowledgement: a valid inference request receives a sequence-matched ACK.
  10. Runtime start: the application prepares interrupt state and calls tvmgen_default_run().
  11. NPU execution: generated code copies microcode/parameters into the TINIElite SRAM windows and starts a hardware stage.
  12. Completion: DONE IRQ 41 enters the small driver ISR, which acknowledges the interrupt, increments a counter, and gives a semaphore.
  13. Continuation: the application wakes and calls the generated TI_NPU_NNC_IRQHandler() in thread context. The runtime either launches another stage or marks the graph finished.
  14. Response: firmware returns three scores, accelerator wait time, runtime time, total time, completion count, spurious count, and CRC.
  15. Verification: the host checks frame integrity, sequence, exact scores, nonzero completions, zero spurious IRQs, and optional stress/fault-test criteria.

10. Ownership, proof, and project boundaries

Implemented and validated
  • Zephyr platform integration.
  • Clock, pinctrl, UART, and NPU glue.
  • Interrupt completion and bounded recovery.
  • Watchdog supervision.
  • Framed protocol and host client.
  • WSL-native build/flash/test.
  • Automated software and hardware evidence.
Provided externally
  • Trained neural-network model.
  • Generated mod.a and header.
  • Six golden vectors.
  • TI NPU runtime internals inside the archive.
  • Hardware documentation and UniFlash tooling.
Do not overclaim
Six fixtures are a regression set, not an accuracy dataset. There is no source model, training code, independent labeled dataset, CPU-equivalent artifact, or power measurement. The system is a strong hardware-validated engineering prototype, not a production-certified product.

10.1 What proves real NPU use?

  • The linked ELF contains generated TINIElite convolution and pooling symbols.
  • The generated archive calls project-supplied NPU instruction/parameter memory callbacks.
  • Physical IRQ 41 produces exactly five acknowledged completions per inference.
  • The host rejects a result with zero completions or any spurious completion.
  • A deliberate missing-completion test reaches the real semaphore timeout path and resets cleanly.

Timing alone is not treated as proof. Direct symbol, MMIO, interrupt, and fault-path evidence is stronger.

11. How to explain it aloud

Thirty-second version

I built the platform and reliability layers needed to run a TVM-generated waveform classifier on TI's AM13E230 microcontroller under Zephyr. A Python client quantizes 256 samples and sends them through a CRC-protected UART protocol. The firmware runs a hybrid CPU/NPU graph, waits for real TINIElite completion interrupts, and returns three class scores plus timing and interrupt evidence. I also added clock validation, NPU timeout recovery, an independent hardware watchdog, WSL-native flashing, tests, and CI. I integrated the supplied binary model; I did not train it.

Two-minute version

The target was a preview TI AM13E230 LaunchPad with a Cortex-M33 and a TINIElite neural accelerator. The only model-side inputs were a generated static library, its header, and six reference vectors, while the pinned Zephyr version did not support the board. I created an out-of-tree board and SoC port, configured the real 200 MHz clock tree and flash wait states, and implemented pinctrl, polling UART, and the NPU adapter expected by the generated binary. On the host, Python reproduces the model's int8 preprocessing and exchanges versioned, sequence-numbered, CRC-32 frames with the firmware. During inference, the generated runtime alternates between CPU orchestration and NPU stages. IRQ 41 is acknowledged in a small ISR, which signals a semaphore; the application continues the generated runtime in thread context with a 100 ms bound. A timeout produces a structured error and cold reset because the binary runtime may retain opaque state. A separate four-second hardware watchdog covers total firmware deadlock. The complete flow builds, flashes, and tests natively in WSL. On hardware, six fixtures passed exactly, and a 600-inference run produced 3,000 acknowledged NPU interrupts, zero spurious interrupts, and zero transport retries. Those are regression results, not a claim of general model accuracy.
